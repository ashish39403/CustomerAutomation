# Implementation Plan
## AI E-commerce Customer Support Automation

**Goal:** one local, working V1. An operator connects a test Gmail inbox, inbound mail becomes a ticket, the worker classifies and drafts from the knowledge base, and the operator reviews and sends a reply in the original thread.

**Shape:** modular monolith. FastAPI and a worker are separate processes from one backend. PostgreSQL is the source of truth. Qdrant is only the retrieval index. The model proposes; Python policy decides. Human approval is the default. Auto-send stays off.

**Local run (end state):** Docker Compose starts the API, worker, Qdrant, and the React app. `DATABASE_URL` points at Neon (or a Compose Postgres service with the same schema). Neon Object Storage (via the branch's S3 endpoint) and Gmail stay external services called from the local processes. One command starts the stack; the README lists the env vars from the tech stack.

**Already in the repo:** `pyproject.toml`, `uv.lock`, and these docs. No application code yet. Add the missing runtime packages (SQLAlchemy, Alembic, Qdrant client, boto3, structlog, tenacity) in Phase 1 and lock them. Stay on Python 3.14 only if those packages import cleanly; otherwise pin 3.13.

**Out of this plan:** multi-inbox, order or payment actions, Redis/Celery, auto-send, and any channel other than Gmail.

---

## Phase 1 — Foundation, auth, and schema

Stand up the backend skeleton and the tables every later phase writes to.

- `backend/app` layout from the architecture doc: `core`, `db`, `modules`, `api`, `tests`.
- Settings, structured logging with redaction, error handlers, `/api/v1/health` and `/api/v1/health/ready`.
- SQLAlchemy 2 + Alembic. Tables: `users`, `gmail_accounts`, `tickets`, `messages`, `ai_runs`, `documents`, `document_chunks`, `jobs`, `send_attempts`, `audit_events`, plus a Gmail history cursor.
- Indexes on Gmail thread/message IDs, ticket status and category, job availability, and audit timelines.
- Fixed roles only: `operator` and `admin`. Session cookie login (`HttpOnly`, `SameSite`). Seed one of each for local use. `/api/v1/auth/me`.
- Compose file with API, worker placeholder, and Qdrant. `.env.example` matches the tech-stack variable list.

**Done when:** migrations apply on an empty database, health reports database readiness, both roles can log in, and a concurrent-safe schema test passes.

## Phase 2 — Job queue and worker

Make long work durable before any Gmail or model call exists.

- Job states: `queued`, `running`, `succeeded`, `retry_wait`, `dead`.
- Claim with `FOR UPDATE SKIP LOCKED` in one transaction. Set `locked_by`, `locked_until`, and increment attempts. Run the handler outside that transaction.
- Transient failures use exponential backoff with jitter. Permanent failures and max attempts become `dead`. A reaper reclaims expired leases.
- Payloads store record IDs only. Handlers are idempotent.
- API: list recent and dead jobs, retry an eligible dead job. Every retry writes an audit event.

**Done when:** two workers cannot claim the same job, a crash mid-handler is recovered by the reaper, and retry does not double-apply a handler.

## Phase 3 — Gmail connect and ingestion

Turn a dedicated test mailbox into tickets.

- OAuth start and callback. Encrypt refresh tokens before storage. Refresh, revocation, and reauthorization states show on the health endpoint.
- Least-privilege Gmail scopes. Poll on an interval using the stored history cursor. On history expiry, resync without skipping mail. Safe initial backfill, bounded.
- Normalize sender, recipients, subject, body, time, Gmail IDs, and attachment metadata. Persist the message, then insert a `process_email` job in the same transaction.
- One ticket per Gmail thread (`gmail_thread_id` unique). One message per `gmail_message_id`.
- Skip the mailbox’s own outbound mail, configured sender exclusions, and automated notifications (`no_reply` path recorded, no customer draft).

**Done when:** a new inbound email creates one ticket, one message, and one job; running the poller again creates nothing extra; excluded and self-sent mail never become customer tickets.

## Phase 4 — Knowledge base

Give the drafter source documents it can cite.

- Admin upload of PDF, TXT, and Markdown. Size, MIME, and extension checks. Private Neon Object Storage key generated by the server. Metadata and checksum in PostgreSQL.
- Document lifecycle: `uploaded → queued → processing → indexed`, or `failed`. Delete path: `deleting → deleted`.
- Worker extracts text, chunks with stable IDs, embeds, and upserts Qdrant points carrying `document_id`, version, chunk id, and source locator.
- Replacement indexes the new version first, then switches the active version and removes old vectors. Retrieval filters to active versions only.

**Done when:** an uploaded policy becomes searchable, a replacement does not leave stale chunks, and delete removes the file from both Neon Object Storage and retrieval.

## Phase 5 — Classification, retrieval, and policy

Process `process_email` into a decision the dashboard can show. No sending in this phase.

- Pipeline order: input guard → structured classification → schema validation → deterministic risk policy → Qdrant retrieval → grounded draft → grounding checks → backend decision.
- Classifier returns category, summary, priority, entities, risk flags, and confidence. Invalid model output is a failed AI run, not a guess.
- Decisions: `needs_review`, `escalate`, `no_reply`. `auto_send` exists in the policy module and is hard-disabled. Refunds, payments, cancellations, legal threats, chargebacks, account security, personal-data requests, and anything that needs live order data always escalate.
- Insufficient or contradictory evidence returns `insufficient_evidence` and escalates. Drafts may not invent order status, refund completion, or delivery dates.
- Persist `ai_runs` (model, prompt version, sources, draft, decision, latency, token usage) and an audit event. Email text and KB text stay untrusted data; they cannot grant tools or change policy.

**Done when:** a routine policy question lands in `needs_review` with citations, a refund or injection email escalates, and a missing-policy email does not produce an unsupported factual reply.

## Phase 6 — Review actions and Gmail send

Close the operator loop on the API.

- Save draft edits. Escalate, resolve, reopen, and assign. Each action checks role and ticket state, then appends an audit event.
- Send: lock and re-check eligibility, write `send_attempt = pending`, commit, call Gmail in-thread, then mark `sent` and store the outbound message. Do not hold a database transaction across the Gmail call.
- A failed send stays failed and does not mark the ticket `replied`. An unknown outcome is reconciled from the thread before any retry. The idempotency key blocks a second reply.
- Ticket statuses used in practice: `new`, `processing`, `needs_review`, `escalated`, `replied`, `resolved`, `failed`.

**Done when:** one approval produces one in-thread reply; a timeout leaves `unknown` and a retry does not send a second email; a rejected or escalated ticket cannot be sent.

## Phase 7 — Operator dashboard

Build the React app against the real API. No fake tickets presented as live data.

- Vite, TypeScript, Tailwind, shadcn/ui, React Router, TanStack Query, React Hook Form, Zod.
- Login. Ticket list with status, category, priority, and date filters. Ticket detail with thread, summary, classification, risk flags, sources, and draft.
- Draft editor with save, approve and send, reject, and escalate. Knowledge-base list, upload, status, and delete. Failed jobs with retry. Audit timeline. Gmail connection and system health for admins.

**Done when:** an operator can sign in, open a processed ticket, edit the draft, and send it, and an admin can upload a document and see it reach `indexed` or `failed`.

## Phase 8 — Local end-to-end proof

This phase finishes the product. After it, the system runs locally and meets the PRD acceptance criteria.

- Docker Compose brings up API, worker, Qdrant, and the dashboard with health checks and restart policies. Document Neon (or local Postgres), the Neon Object Storage env vars (`neon env pull` for the S3 endpoint and branch credentials), Gmail OAuth redirect, and seed users in the README.
- Versioned golden set, with no live customer PII: shipping and product questions, missing and contradictory policy, refund and payment, angry or threatening mail, prompt injection, spam, duplicates, and malformed mail. Score classification, risk-case recall, retrieval hit rate, and unsupported-answer rate.
- Automated tests for the policy matrix, idempotent ingest, job claim and lease recovery, and the send state machine including the unknown-outcome path.
- Walk the local test inbox once and record the result: connect, ingest once, classify, retrieve, escalate a refund, approve a safe draft, confirm a single thread reply, show a failed send, and confirm delete drops a document out of retrieval.

**Done when:** a new machine can follow the README, start the stack, and complete that walkthrough. That is V1.
